Plant Simulation Tutorial

4. แรงงานและทรัพยากรบุคคล

วัตถุประสงค์การเรียนรู้

  1. เข้าใจว่า WorkerPool/Broker/Workplace ทำงานร่วมกันอย่างไร
  2. อธิบายความต่างของ 3 เฟรมที่ค่อยๆ เพิ่มความซับซ้อนของระบบแรงงานได้

อ้างอิงเฟรม Model_Basic_Worker, Model_Workers, Model_Worker_Service — เรียงความซับซ้อนจากน้อยไปมาก สาธิตการจำลองคนงานที่ต้องใช้ร่วมกันระหว่างหลายสถานี ดูภาพรวม Object กลุ่มนี้เพิ่มที่ Object Reference บทที่ 3

สามชิ้นส่วนของระบบแรงงาน

Objectหน้าที่
WorkerPool"คลัง" คนงานที่มีอยู่ในระบบ — กำหนดจำนวนคนและกะการทำงานที่นี่
Brokerตัวกลางจับคู่ระหว่างคำขอแรงงานจาก Workplace กับคนงานว่างใน WorkerPool
Workplaceจุดที่ผูกกับ Station ซึ่งต้องมีคนงานอยู่ด้วยจึงจะเริ่มประมวลผลได้

ทั้งสามตัวทำงานร่วมกันเสมอเป็นชุด — ถ้าลืม Broker คนงานใน WorkerPool จะไม่ถูกจ่ายงานให้ Workplace เลย

Model_Basic_Worker — จุดเริ่มต้น

เฟรมนี้มี Station เดียวกับ Workplace เดียว: คนงาน 1 คนจาก WorkerPool ถูก Broker ส่งไปช่วยที่ Workplace เมื่อมีชิ้นงานมาถึง รันแล้วสังเกตว่า Station จะ "รอคนงาน" (Waiting on Worker) ก่อนเริ่มประมวลผลทุกครั้งที่มีชิ้นงานใหม่เข้ามา

Model_Workers — คนงานร่วมกันหลายสถานี

เพิ่มจำนวน Station/Workplace เป็น 4-6 จุด แต่ WorkerPool ยังมีจำนวนคนงานจำกัด — สาธิตสถานการณ์จริงที่คนงานไม่พอสำหรับทุก สถานีพร้อมกัน Broker ต้องตัดสินใจว่าจะส่งคนงานไปช่วยจุดไหนก่อน

Tip: ถ้า Throughput ต่ำกว่าที่คาด ให้เช็คสถิติของ Broker ก่อน — มักเป็นเพราะจำนวนคนงานใน WorkerPool น้อยเกินไปเทียบกับจำนวนจุดที่ต้องการพร้อมกัน ไม่ใช่ปัญหาที่ Station เอง

Model_Worker_Service — คนงานเดินบริการหลายจุด

รูปแบบซับซ้อนที่สุด: คนงานไม่ได้ประจำอยู่กับ Station เดียวตลอดกะ แต่เดินไปมาให้บริการหลายสถานีตามคิวที่เกิดขึ้นจริง (roaming service) เหมาะจำลองสถานการณ์เช่น ช่างเทคนิคที่ดูแลหลายเครื่องจักร

คำถามฝึกคิด: ทำไมไฟล์สอนถึงแยกเป็น 3 เฟรม (Basic_Worker → Workers → Worker_Service) แทนที่ จะรวมเป็นเฟรมเดียว?

เฉลย: เพื่อแยกตัวแปรที่เพิ่มความซับซ้อนทีละตัว — จากคนงาน 1 คน/สถานีเดียว ไปสู่คนงานจำกัดที่ต้องแบ่งกันหลายสถานี ไปสู่คนงานที่เดินบริการเชิงรุก ถ้าเรียนรวมทีเดียวจะแยกไม่ออกว่าพฤติกรรมไหนมาจาก Object ไหน
